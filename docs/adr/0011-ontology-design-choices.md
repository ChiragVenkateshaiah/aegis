# ADR-0011: Ontology Design Choices

**Date:** 2026-05-17
**Status:** Accepted

---

## Context

Day 1 of the AEGIS build produces the Postgres 16 DDL that every later module
(extraction, reconciliation, ratios, memo) binds to. Several design calls had to
be made during implementation. This ADR captures the decisions so future-Chirag
doesn't re-litigate them in Phase 2.

---

## a. Inheritance model for tax_returns / bank_statements

**Decision: table-per-subtype (TPT) — shared-PK pattern.**

Each subtype table (`tax_returns`, `bank_statements`) has a UUID primary key that
is also a foreign key to `documents.id`. The base `documents` table retains a
`doc_type` TEXT discriminator for fast filtering without a join.

**Alternatives considered:**

- **Single table with NULL columns (STI).** Rejected. `tax_returns` has `form_type`,
  `tax_year`, `fiscal_year_end`, `preparer_name`; `bank_statements` has `bank_name`,
  `account_number_last4`, `statement_month`, `account_type`. Merging these into one
  table means every row has ~4 nullable columns that belong to the wrong subtype. At
  the scale of a credit-file corpus (tens of thousands of documents) this is fine
  technically, but it creates confusion for anyone writing queries and makes adding a
  third doc type (e.g. personal 1040 in Phase 3) require altering a shared table.

- **Concrete table inheritance (CTI).** Rejected. CTI duplicates the base columns
  (filename, file_hash, page_count, borrower_id, etc.) in each subtype table, making
  cross-subtype queries harder and base-column changes require altering multiple tables.

**TPT tradeoffs:**
- Pro: clean subtype columns; adding a third doc type is a new table + FK, not an ALTER.
- Pro: `SELECT * FROM documents` gives a clean document listing; subtype detail requires one JOIN.
- Con: every subtype fetch needs a join. Acceptable for v1 read patterns.

## b. Provenance column shape

**Decision: inline provenance block on every fact-bearing table.**

Every table that holds an extracted or computed fact
(`line_items`, `ratios`, `reconciliations`, `exception_flags`, `memo_citations`)
carries these six columns directly:

| Column | Type | Notes |
|--------|------|-------|
| `source_document_id` | UUID FK → documents | RESTRICT cascade |
| `page_number` | INTEGER | 1-indexed; nullable for computed rows |
| `bounding_box` | JSONB | `{x0, y0, x1, y1, units}`; nullable |
| `extractor_model` | TEXT | model name + version slug |
| `confidence` | NUMERIC(4,3) | 0.000–1.000; CHECK constraint |
| `raw_blob` | JSONB | full extracted context for re-derivation |

**Alternatives considered:**

- **Separate `provenance` table with a polymorphic FK.** Rejected. Polymorphic FKs
  in Postgres require either nullable FKs on all fact tables or a generic `fact_type`
  + `fact_id` pair (no referential integrity). The join overhead and integrity tradeoff
  is not worth it for v1.

- **JSONB provenance blob on each row.** Considered as a middle ground but rejected
  because queryable fields (`source_document_id`, `confidence`) would lose indexability
  and type safety. `raw_blob` already covers the unstructured remainder.

**Why RESTRICT on `source_document_id`:** a document is evidence. If a document is
deleted, the system should throw an error rather than silently orphaning the facts that
cite it. Soft-delete (`deleted_at`) is available on all base tables; hard deletes should
be explicit and audited.

**Why `raw_blob` JSONB:** the raw extracted context (OCR text, raw JSON from the model
response, surrounding paragraph) is needed to re-derive or audit a value without
re-running the extraction pipeline. This is the reliability backbone referenced in ADR-0009.

## c. FK cascade choices

| Relationship | ON DELETE | Rationale |
|---|---|---|
| `owners → borrowers` | CASCADE | An owner without a borrower is meaningless |
| `entities → borrowers` | CASCADE | Same — entity is an extension of borrower |
| `financial_periods → entities` | CASCADE | Period belongs to entity |
| `documents → borrowers` | RESTRICT | Documents are evidence; don't silently delete |
| `documents → entities` | RESTRICT | Same |
| `documents → financial_periods` | RESTRICT | Same |
| `tax_returns → documents` | CASCADE | Subtype row follows its base document |
| `bank_statements → documents` | CASCADE | Same |
| `line_items → documents` | CASCADE | Items are derived from and owned by a document |
| `line_items → financial_periods` | RESTRICT | Period reference is evidentiary |
| `ratios → entities` | RESTRICT | Computed artifact; don't cascade |
| `ratios → financial_periods` | RESTRICT | Same |
| `reconciliations → entities` | RESTRICT | Cross-doc check is a finding record |
| `reconciliations → financial_periods` | RESTRICT | Same |
| `exception_flags → reconciliations` | CASCADE | A flag is generated by its reconciliation |
| `exception_flags → entities` | RESTRICT | Direct entity reference is independent |
| `memos → borrowers` | RESTRICT | Memo is a deliverable; don't cascade |
| `memos → entities` | RESTRICT | Same |
| `memos → financial_periods` | RESTRICT | Same |
| `memo_citations → memos` | CASCADE | Citations are part of a memo |
| `memo_citations → line_items` | RESTRICT | Citation anchors to evidence |
| `memo_citations → ratios` | RESTRICT | Same |
| `memo_citations → reconciliations` | RESTRICT | Same |
| All `source_document_id` (provenance) | RESTRICT | Evidence must not silently disappear |

## d. Intentionally NOT modeled in v1

The following were considered and deferred:

1. **Personal tax returns (1040 / Schedule C).** Owner-DTI analysis needs personal
   financials. The `owners` table has placeholder fields (`credit_score`, `ssn_last4`)
   but no document subtype. Deferred to Phase 3.

2. **Audited financial statements.** A third doc type (`audited_financials`) with an
   income statement / balance sheet structure. Deferred to Phase 4; the TPT inheritance
   model makes adding it a new table + new rows, no ALTER required.

3. **Multi-currency.** All amounts carry a `currency CHAR(3)` column (defaulting to
   `'USD'`) so the schema doesn't need migration when we support non-USD borrowers.
   The ratio engine and reconciliation logic are USD-only in v1.

4. **Loan / facility table.** The credit memo describes a requested loan, but we have
   no table to store loan terms, requested amount, collateral, or proposed structure.
   This is intentional: v1 produces a memo about the borrower's financials, not a
   decisioning system. Loan-level tables belong in Phase 5+.

5. **Users / auth.** No `users` table, no row-level security. A future multi-tenant
   deployment will need this but it is out of scope for the portfolio demo.

6. **Versioning / history tables.** No event-sourcing or audit-log tables. The
   `updated_at` + `deleted_at` pattern is the minimal concession to auditability;
   full version history is deferred to Phase 5.

7. **Full-text search indexes.** No `tsvector` columns or GIN indexes on text fields.
   If free-text search on memo body or line_item labels becomes necessary, it can be
   added as a migration without schema changes to fact tables.

---

## Consequences

- **Positive:** Every later module (extraction, reconciliation, ratios, memo) has a
  stable contract. The evidence model is explicit and auditable.
- **Positive:** The TPT approach means adding a third doc type in Phase 3 is additive,
  not destructive.
- **Negative / risk:** Provenance columns are repeated inline across 5 tables. If the
  provenance shape changes (e.g. adding a `model_temperature` column), all 5 tables
  need ALTER. Acceptable for v1; a composite domain type in Postgres 16 could reduce
  this in a future migration.
- **Follow-ups:**
  - Phase 2: Add SQLAlchemy ORM models mirroring this DDL. See `src/aegis/ontology/`.
  - Phase 3: Add `personal_tax_returns` subtype + expand `owners`.
  - Phase 5+: Add loan/facility table, auth/user table, version history.
